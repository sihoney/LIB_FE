도서·회원·대출의 관계, 데이터, 업무 규칙과 검증 사례를 기록한다. 도서관 기능을 구현하면서 MES의 책임 분리를 학습하며, MSW로 먼저 동작을 확인한 뒤 같은 계약으로 LIB_BE에 연결한다.

- 설계 상태: 도서 정책 6개는 사용자 합의로 확정했다. 나머지는 정책 결정표에 따라 미확정 초안으로 유지한다.
- 구현 상태: 도서 목록·등록·수정·논리 삭제의 HTTP 핸들러, Repository·Service·화면과 고정 Mock 데이터·재고 계산을 연결했다. 회원·대출 업무는 미구현이다. 학습용 공지글 CRUD와 공통 기반은 구현되어 있다.

## 2. 도메인 관계와 책임

```text
Book 1 ─── N Loan N ─── 1 Member
                           │
                           └── Account (로그인 계정)
```

- 도서·회원·대출 업무는 `modules/lib`, 로그인 계정·비밀번호·역할·접근 제어는 `modules/sys`가 담당한다.
- 대출은 `bookId`, `memberId`로 도서와 회원을 참조한다. 대출 한 건은 책 한 권의 대출이다.
- 회원은 `accountId`로 계정 하나에 연결한다. 한 계정에 여러 회원을 연결하지 않는다.
- 관리자 계정은 회원 업무 정보 없이 존재할 수 있다. 따라서 계정에 연결된 회원은 0명 또는 1명이다.
- 회원가입과 관리자 회원 등록은 중복 회원을 만들지 않도록 같은 계정·회원 생성 규칙을 사용한다. 생성 절차와 실패 시 처리 계약은 인증 구현 단계에서 확정한다.

이 관계는 설계 제안이다. 현재 Book 타입과 재고 계산용 최소 Mock 대출 계약만 작성했으며, DB 테이블과 전체 회원·대출 DTO는 미구현이다.

## 3. 도서 Book

도서 한 건은 같은 도서로 묶어 관리하는 제목·저자·분류 정보와 총 보유 수량을 의미한다. 같은 도서의 물리적인 책 한 권씩은 식별하지 않는다.

### 저장 필드 초안

| 필드            | 의미           | 제약                         |
| --------------- | -------------- | ---------------------------- |
| `id`            | 도서 ID        | 양의 정수, 생성 후 변경 불가 |
| `title`         | 제목           | 필수, 앞뒤 공백 제거         |
| `author`        | 저자           | 필수, 앞뒤 공백 제거         |
| `category`      | 분류 코드      | 허용된 코드 사용             |
| `totalQuantity` | 총 보유 수량   | 0 이상의 정수                |
| `isDeleted`     | 논리 삭제 여부 | 기본값 `false`               |

분류는 문학(`LITERATURE`)·과학(`SCIENCE`)·역사(`HISTORY`)·기타(`OTHER`) 중 선택한다. 제목·저자는 앞뒤 공백을 제거한 후 필수 검증하며, 제목은 최대 200자, 저자는 최대 100자다. 동일 제목은 허용한다.

### 계산 필드와 규칙

```text
미반납 수량 = returnedAt이 null이고 cancelledAt이 null인 대출 건수
availableQuantity = totalQuantity − 미반납 수량
대출 가능 여부 = availableQuantity > 0
```

`availableQuantity`는 조회 응답에 포함하고 등록·수정 요청에서는 받지 않는다. 별도 가용 수량을 저장·수정하여 대출 기록과 어긋나게 만들지 않는다.

- 총 보유 수량은 미반납 수량보다 작게 수정할 수 없다.
- 미반납 대출이 있는 도서는 삭제할 수 없다.
- 삭제 시 데이터와 ID를 남겨 대출 이력을 보존한다. 일반 도서 검색과 신규 대출 대상에서는 제외한다.
- 제목 중복만으로 등록을 차단하지 않는다.

도서별 수량 관리, 가용 수량 계산, 논리 삭제와 미반납 시 삭제 차단, 보유 수량 수정 제한, 분류 선택, 제목·저자 입력 규칙은 2026-10-14 사용자 합의로 확정했다. 목록 검색·페이징과 도서 등록·수정의 화면·HTTP 경계 입력 검증, Mock 가용 수량 조회를 구현했다. 삭제 처리는 미구현이다.

### 등록 API 계약

`POST /v2/Lib/Book/Create/Update`를 사용한다. `IBookCreate`는 `title`, `author`, `category`, `totalQuantity`만 받으며 ID·삭제 여부·가용 수량은 서버가 결정한다.

- 제목·저자는 앞뒤 공백 제거 후 각각 1~200자, 1~100자여야 한다.
- 분류는 허용 코드 중 하나이며 보유 수량은 0 이상의 안전한 정수여야 한다.
- 동일 제목 등록은 허용한다. 성공 시 새 ID와 `isDeleted: false`를 가진 저장 도서를 응답한다.
- 잘못된 요청은 HTTP 200의 `success: false`, `returnMessCode: 'INVALID_BOOK_CREATE_REQUEST'`, `data: null`로 응답한다. 실패는 Mock 배열을 변경하지 않는다.
- Service는 성공 후 목록 Query key 접두어를 무효화한다. 화면이 배열을 직접 변경하지 않고, 활성 목록은 다시 조회한 서버 응답으로 갱신한다.

### 수정 API 계약

`POST /v2/Lib/Book/Update/Update`를 사용한다. 메서드 이름은 `patchBook`이지만 MES 규약의 실제 HTTP 요청은 POST다. `IBookUpdate`는 양의 안전한 정수 ID와 등록 필드를 모두 받는다.

- 제목·저자·분류·보유 수량은 등록과 같은 입력 정책을 적용한다.
- 삭제되지 않은 대상 도서만 수정할 수 있다. 없는 ID는 `BOOK_NOT_FOUND` 실패 응답이다.
- 보유 수량은 해당 도서의 미반납·미취소 대출 수량 이상이어야 한다. 그렇지 않으면 `BOOK_QUANTITY_BELOW_OUTSTANDING` 실패 응답이며 데이터는 변경하지 않는다.
- 형식이 잘못된 요청은 `INVALID_BOOK_UPDATE_REQUEST` 실패 응답이다.
- 성공 후 목록 Query를 무효화한다. 목록의 가용 수량과 수정 제한은 같은 미반납 수량 계산 함수를 사용한다.

### 삭제 API 계약

`POST /v2/Lib/Book/Delete/Update`를 사용한다. `IBookDelete`는 양의 안전한 정수 ID만 받는다. 실제 데이터는 삭제하지 않고 `isDeleted: true`로 변경해 대출 이력을 보존한다.

- 삭제되지 않은 대상 도서만 삭제할 수 있다. 없는 ID나 이미 삭제된 대상은 `BOOK_NOT_FOUND` 실패 응답이다.
- 미반납·미취소 대출이 한 건이라도 있으면 `BOOK_HAS_OUTSTANDING_LOANS` 실패 응답이며 데이터는 변경하지 않는다.
- 형식이 잘못된 요청은 `INVALID_BOOK_DELETE_REQUEST` 실패 응답이다.
- 성공 후 목록 Query 접두어를 무효화한다. 목록 API는 논리 삭제된 도서를 계속 제외한다.

### 목록 API 계약

`POST /v2/Lib/Book/GetBookList/GetData`를 사용한다. `BOOK_MODULE`과 `BOOK_LIST_META`로 경로를 구성한다. 이 경로의 HTTP 핸들러와 목록 화면을 연결했다.

- 요청: `IBookListRequest = IRequestBody<IBookSearch>`.
- 응답: `IBookListResponse`. 공통 `IResponseBody<IBookListItem[]>`를 사용하되 `totalRecords`는 필수다.
- `IBook`은 저장 정보다. `IBookListItem`은 `isDeleted`를 제외하고 계산된 `availableQuantity`를 포함한다.
- 제목·저자는 앞뒤 공백을 제거하고 대소문자를 구분하지 않는 부분 일치로 검색한다. 생략·공백뿐인 문자열은 해당 조건을 적용하지 않는다.
- 분류는 코드의 정확한 일치로 검색한다. 여러 검색 조건은 AND로 결합한다. 허용되지 않은 분류 코드는 실패 응답으로 처리한다.
- 삭제된 도서를 먼저 제외하고 검색 → 가용 수량 계산 → 사용자 지정 정렬 → ID 오름차순 보조 정렬 → 페이징 순서로 처리한다.
- `sortings`는 MES 공통 계약인 `{ columName, typeSorting: 'ASC' | 'DESC' }` 배열이다. 제목·저자·분류·보유 수량·가용 수량만 허용하며, 같은 열을 중복 지정하거나 허용하지 않은 열·방향을 보내면 실패 응답이다.
- `skip`은 0 이상의 안전한 정수이며 기본값은 0이다. `take`도 0 이상의 안전한 정수이며 기본값은 기존 HttpClient와 동일한 20이다. `take: 0`은 `skip` 이후 전체 조회다.
- `totalRecords`는 검색 후·페이징 전 건수다. 범위를 벗어난 `skip`이면 빈 배열을 반환하되 전체 건수는 유지한다.
- 잘못된 검색·페이징 요청은 HTTP 200의 `success: false`, `returnMessCode: 'INVALID_BOOK_LIST_REQUEST'`, 설명 메시지, `data: []`, `totalRecords: 0`으로 응답한다. 재고 데이터 불일치는 요청 오류나 빈 결과로 숨기지 않고 서버 오류로 처리한다.

기본 조회 요청 예시:

```json
{
	"data": {},
	"skip": 0,
	"take": 1
}
```

현재 고정 데이터 기준 응답 예시:

```json
{
	"success": true,
	"returnMess": "",
	"returnMessCode": 0,
	"data": [
		{
			"id": 1,
			"title": "도서관의 하루",
			"author": "김하늘",
			"category": "LITERATURE",
			"totalQuantity": 3,
			"availableQuantity": 3
		}
	],
	"totalRecords": 5
}
```

검색 결과가 없으면 `success: true`, `data: []`, `totalRecords: 0`이다. 이 절의 검색·페이징·오류 응답을 핸들러에서 구현했다. 타입 정의와 별도로 HTTP 경계에서 입력값을 검증한다.

## 4. 회원 Member

### 저장 필드 초안

| 필드          | 의미           | 제약                                         |
| ------------- | -------------- | -------------------------------------------- |
| `id`          | 회원 ID        | 양의 정수, 생성 후 변경 불가                 |
| `accountId`   | 로그인 계정 ID | 필수 연결, 계정 ID 타입은 인증 계약에서 확정 |
| `name`        | 이름           | 필수                                         |
| `phone`       | 연락처         | 필수                                         |
| `email`       | 이메일         | 필수, 형식 검증                              |
| `status`      | 회원 상태      | `ACTIVE` 또는 `WITHDRAWN`                    |
| `joinedAt`    | 가입 일시      | 생성 시 기록                                 |
| `withdrawnAt` | 탈퇴 일시      | 정상 회원은 `null`                           |

### 업무 규칙 초안

- 미반납 대출이 있으면 탈퇴할 수 없다.
- 탈퇴 후에도 회원 데이터와 대출 이력을 보존한다.
- 탈퇴 회원은 로그인·신규 대출을 할 수 없다. 계정 차단과 기존 세션 처리는 인증과 연결한다.
- 이름·연락처는 중복될 수 있으므로 회원 식별자로 사용하지 않는다.
- 일반 회원은 자신의 이름·연락처·이메일만 수정할 수 있다. 역할·회원 상태·계정 연결은 변경할 수 없다.

이메일 필수 여부, 연락처 형식·정규화, 입력 길이는 회원 구현 전에 최종 확정한다.

## 5. 대출과 반납 Loan

대출 한 건은 회원 한 명이 도서 한 권을 빌린 기록이다. 같은 도서 두 권을 빌리면 대출 기록도 두 건이다. 반납은 대출 ID로 대상을 식별한다.

### 저장 필드 초안

| 필드           | 의미           | 제약                             |
| -------------- | -------------- | -------------------------------- |
| `id`           | 대출 ID        | 양의 정수, 생성 후 변경 불가     |
| `bookId`       | 도서 ID        | 존재하는 도서 참조               |
| `memberId`     | 회원 ID        | 존재하는 회원 참조               |
| `loanedAt`     | 대출 일시      | 처리 시 기록                     |
| `dueDate`      | 반납 예정일    | 날짜 단위                        |
| `returnedAt`   | 실제 반납 일시 | 미반납이면 `null`                |
| `cancelledAt`  | 취소 일시      | 취소되지 않았으면 `null`         |
| `cancelReason` | 취소 사유      | 취소 시 필수, 정상 기록은 `null` |

일시는 시간대가 명확한 형식, 예정일은 `YYYY-MM-DD`를 사용한다. 구체적인 API 직렬화 계약은 LIB_BE와 맞추며, 시간대 없는 일시 문자열을 임의로 해석하지 않는다.

### 조회 상태 계산

아래 순서로 판정하며 상태는 별도로 저장하지 않는다.

| 조건                                         | 조회 상태 |
| -------------------------------------------- | --------- |
| `cancelledAt` 존재                           | 취소      |
| 취소되지 않았고 `returnedAt` 존재            | 반납완료  |
| 미반납이며 도서관 기준 오늘이 `dueDate` 이후 | 연체      |
| 나머지 미반납                                | 대출중    |

반납과 취소가 동시에 기록되는 상태는 허용하지 않는다. 연체 후 반납한 기록도 상태는 반납완료이며 연체일수·연체료를 별도로 표시한다. 취소는 필수 상태 필터와 별도로 이력에서 확인할 수 있도록 제안한다.

### 대출 처리

1. 정상 회원인지 확인한다.
2. 해당 회원에게 미반납 연체가 있는지 확인한다.
3. 도서가 존재하고 삭제되지 않았는지 확인한다.
4. 대출 가능 수량이 1권 이상인지 확인한다.
5. 대출일·예정일을 결정하고 대출 기록을 생성한다.

검증 실패 시 기록을 생성하지 않는다. 실제 BE에서는 재고 확인과 기록 생성을 트랜잭션 및 동시성 제어로 보호해야 한다. Mock의 순차 처리 성공을 실제 서버 동시성 검증으로 간주하지 않는다.

### 반납 처리

1. 대출 ID로 기록을 찾는다.
2. 취소되거나 이미 반납된 기록이면 거부한다.
3. 실제 반납 일시를 기록한다.

가용 수량은 미반납 건수 감소로 계산에 반영된다. 별도의 수량 증가 요청을 보내지 않는다.

### 수정과 삭제의 업무 의미

| CRUD | 제안한 업무 동작          |
| ---- | ------------------------- |
| 생성 | 대출 처리                 |
| 조회 | 목록·상세·회원별 이력     |
| 수정 | 관리자의 반납 예정일 정정 |
| 삭제 | 잘못 등록한 대출의 취소   |

- 예정일 정정은 미반납·미취소 건에 한해 허용하고 대출일보다 이른 날짜는 금지한다.
- 회원·도서 선택 오류는 취소 후 재등록으로 처리한다.
- 취소는 미반납 건에 한해 허용하고 사유와 일시를 남긴다. 기록을 물리 삭제하지 않는다.
- 반납 완료 기록의 취소와 별도 대출 연장은 초기 범위에서 제외하는 안이다.

수정·삭제의 처리 방식과 정정 사유·변경 이력 보관 수준은 미확정이다. 대출 CRUD 구현 전에 확정한다.

## 6. 정책 결정표

`필수`는 요구사항에 명시된 규칙이다. `확정`은 사용자와 합의한 정책이며 구현 완료를 의미하지 않는다. `제안·미확정`은 이 초안의 가정이며 구현 완료나 사용자 승인으로 취급하지 않는다.

| 정책                | 값 또는 방향                                                     | 근거                     | 상태        |

## 7. 화면과 접근 권한

| 사용자    | 업무 범위                                                       |
| --------- | --------------------------------------------------------------- |
| 관리자    | 도서·회원 관리, 대출·반납·정정·취소, 전체 이력·현황·대시보드    |
| 일반 회원 | 도서 검색, 본인 대출 현황·이력·연체료 조회, 본인 정보 조회·수정 |

회원의 직접 대출·반납 버튼은 요구 화면에 없으므로 초기 흐름은 관리자가 처리한다. 본인 정보는 요청의 회원 ID만 신뢰하지 않고 인증된 계정과 연결해 제한한다. 메뉴·라우트 제한과 API 권한 검증을 각각 구현하며, 실제 보장은 LIB_BE에서 수행한다.

## 8. 계층과 구현 순서

```text
Page / 업무 Component → Service → Repository → HttpClient
                                                    ↓ HTTP
                                      MSW 또는 실제 LIB_BE
```

- Page는 검색 조건·선택·모달·이벤트를 연결한다.
- Service는 TanStack Query 훅과 변경 후 캐시 갱신을 담당한다. 재고·연체 판정을 UI Service에만 두지 않는다.
- Repository는 API 요청을 담당하며 화면 알림·모달을 제어하지 않는다.
- Mock 업무 로직은 도서·회원·대출 데이터를 함께 참조해 규칙을 검증한다. 일반 Repository와 화면은 Mock 저장소를 직접 읽지 않는다.
- 계산된 재고·상태·집계는 API 응답으로 제공한다. 도서 목록의 가용 수량을 계산하려고 화면에서 전체 대출 데이터를 가져오지 않는다.
- 대출·반납·취소 후에는 도서 재고, 대출 목록, 회원 이력, 대시보드 등 영향을 받는 Query를 갱신한다. 정확한 Query key는 구현 시 정의한다.

파일은 `types/modules/lib/book.ts`, `libMember.ts`, `libLoan.ts`와 각 Repository·Service처럼 도메인별로 배치한다. 인증은 `modules/sys`로 분리한다. 목표 파일을 미리 모두 생성하지 않는다.

구현 순서는 도서 목록 → 도서 CRUD → 회원·인증 → 대출·반납 → 현황·회원 화면이다. 공통 테이블·폼·Base 계층은 실제 반복을 확인한 뒤 도입한다. 목록 API 등의 상세 계약은 각 기능을 구현하면서 추가한다.

## 9. Mock 데이터와 검증 사례

현재 `mocks/data/modules/lib/books.ts`와 `loans.ts`에 도서 6개·재고 계산용 대출 기록 7개를 준비했다. 대출의 `bookId`는 실제 고정 도서 ID를 참조한다. `IMockLoanStockRecord`는 `id`·`bookId`·`returnedAt`·`cancelledAt`만 가진 Mock 전용 계약이다. 회원 연결·대출일·예정일은 아직 없으며 회원·대출 구현 시 확장한다.

`mocks/utils/modules/lib/book.ts`의 `getBookAvailableQuantity`는 전달받은 도서·대출 기록으로 가용 수량을 계산한다. 잘못된 보유 수량이나 재고 초과 대출은 오류로 처리하며 0으로 보정하지 않는다. 삭제 도서 제외·검색·페이징·DTO 조립은 목록 핸들러에서 담당한다.

| 도서 ID | 사례                     | 보유 수량 | 미반납·미취소 | 예상 가용 수량      |
| ------- | ------------------------ | --------- | ------------- | ------------------- |
| 1       | 대출 없음                | 3         | 0             | 3                   |
| 2       | 일부 대출                | 3         | 2             | 1                   |
| 3       | 전부 대출                | 2         | 2             | 0                   |
| 4       | 보유 0권                 | 0         | 0             | 0                   |
| 5       | 반납 1건·취소 1건        | 2         | 0             | 2                   |
| 6       | 삭제 도서, 과거 반납 1건 | 1         | 0             | 1 (목록에서는 제외) |

데이터는 모듈 초기화 때 한 번 생성되는 메모리 배열이다. Faker 대량 데이터는 페이징 구현 시 추가한다. 앞선 목록 초안의 독립된 가용 수량 고정값은 대출 기록에서 계산하는 방식으로 대체했다.

아래 표는 전체 도메인의 검증 목표다. 현재 고정 데이터는 위 6개 사례만 포함하며 연체·회원·권한 사례는 후속 구현 대상이다.

| 사례                            | 확인할 결과                                   |
| ------------------------------- | --------------------------------------------- |
| 대출 이력이 없는 도서           | 가용 수량과 총 보유 수량이 같음               |
| 일부 수량 대출 중               | 미반납 건수만큼 가용 수량 감소                |
| 모든 수량 대출 중               | 가용 수량 0, 신규 대출 거부                   |
| 총 보유 수량 0                  | 목록 표시 가능, 대출 거부                     |
| 오늘 반납 예정                  | 당일까지는 연체 아님                          |
| 예정일 다음 날 미반납           | 연체 1일, 해당 회원의 신규 대출 거부          |
| 정상 반납·연체 후 반납          | 반납일 저장, 재고 반영, 반납 후 연체일수 고정 |
| 중복 반납                       | 두 번째 요청 거부, 재고 중복 반영 없음        |
| 대출 취소                       | 이력 보존, 미반납·재고·연체 집계에서 제외     |
| 미반납 회원 탈퇴·도서 삭제      | 거부, 기존 데이터 유지                        |
| 삭제 도서·탈퇴 회원의 과거 대출 | 이력 조회 가능, 신규 대출 불가                |
| 일반 회원의 타인 기록 요청      | 접근 거부                                     |
| 마지막 1권의 동시 대출          | 실제 BE 검증에서 두 요청 중 한 건만 성공      |

연체 경계 검증에는 고정 기준 날짜를 사용한다. Mock 데이터 영속 저장·초기화·버전 관리와 시나리오 제어는 별도 구현 과제이며 이 문서 작성으로 도입되지 않는다.
